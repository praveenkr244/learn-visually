Part 1 · The test runner

What npx playwright test gives you before you write a single locator.

01

Why @playwright/test?

Playwright comes in two parts: the library that drives browsers, and Playwright Test, a full test runner built around it. The runner is TypeScript-first and needs no Jest, Mocha or TestNG: fixtures, parallel runs, retries, projects, reporters, screenshots, traces and sharding are all built in.

🧩Fixtures

Each test gets a fresh, isolated page and context. Nothing leaks between tests.

⚡Parallel by default

Test files are spread across worker processes. Scale with --workers.

🗂️Projects

Run the same tests in Chromium, Firefox, WebKit and mobile viewports from one command.

📊Reporters

HTML, list, dot, line, JSON, JUnit, blob, plus custom ones. Ready for CI.

Install and run

npm init playwright@latest      # creates playwright.config.ts, tests/, an example test
npx playwright test             # run every test, headless, in parallel
npx playwright show-report      # open the HTML report

02

Test structure, hooks and annotations

A spec file groups tests with test.describe. Hooks run around them: beforeAll/afterAll once per worker for the file or group, beforeEach/afterEach around every test.

import { test, expect } from '@playwright/test';

test.describe('Login module', () => {
  test.beforeAll(async () => { /* runs once */ });

  test.beforeEach(async ({ page }) => {
    await page.goto('/login');
  });

  test('valid login', async ({ page }) => {
    await page.getByLabel('Email').fill('admin@test.com');
    await page.getByLabel('Password').fill('pass123');
    await page.getByRole('button', { name: 'Login' }).click();
    await expect(page).toHaveURL(/dashboard/);
  });

  test.afterEach(async ({ page }) => { /* cleanup */ });
  test.afterAll(async () => { /* runs once */ });
});

Annotations

AnnotationWhat it does
test.skip() · test.skip(cond, 'why')Skip always, or only when the condition is true (e.g. one browser)
test.only()Run only this test. Guard CI with --forbid-only
test.fixme()Known broken: skipped and marked “fixme”
test.fail()Expected to fail; the run fails if it passes
test.slow()Triples this test's timeout
test.describe.configure({ mode: 'serial' })Tests in the group run in order; one failure skips the rest
test.describe.configure({ mode: 'parallel' })Tests inside this one file run in parallel too

03

Fixtures: what { page } really is

The object your test destructures is a set of fixtures. Playwright sets each one up just before the test, hands it over, and tears it down afterwards, so every test starts clean.

FixtureScopeWhat you get
pageper testA new tab in a new browser context
contextper testAn isolated BrowserContext: its own cookies and storage, like an incognito window
browserper workerOne browser instance shared by all tests in that worker
browserNameper project'chromium', 'firefox' or 'webkit'
requestper testAn APIRequestContext for API calls without a page

Your own fixtures: page objects for free

Extend test once, and every test can ask for a ready-made page object by name. Code before use() is setup; code after it is teardown.

// fixtures/base.ts
import { test as base } from '@playwright/test';
import { LoginPage } from '../pages/LoginPage';

type MyFixtures = { loginPage: LoginPage };

export const test = base.extend<MyFixtures>({
  loginPage: async ({ page }, use) => {
    const loginPage = new LoginPage(page);   // setup
    await use(loginPage);                    // the test runs here
    // teardown (optional)
  },
});
export { expect } from '@playwright/test';

// tests/login.spec.ts
import { test, expect } from '../fixtures/base';
test('login', async ({ loginPage }) => {
  await loginPage.login('admin@test.com', 'pass123');
});

05

Which browsers can Playwright drive?

In one line: Playwright can use your installed Chrome and Edge, but uses its own patched builds of Firefox and WebKit, and cannot drive Safari at all. Pick a browser to see how to configure it and why.

BrowserOut of the box?How to configureUses your installed copy?
ChromiumYes...devices['Desktop Chrome']No, Playwright's bundled build
Google ChromeYeschannel: 'chrome'Yes
Microsoft EdgeYeschannel: 'msedge'Yes
FirefoxYes...devices['Desktop Firefox']No, patched build only
WebKitYes...devices['Desktop Safari']No, patched build (Safari's engine)
SafariNoNot possibleUse WebKit as a proxy
Opera, BraveUnofficiallaunchOptions.executablePathYes, Chromium-based, not officially supported

Channels for Chromium-based browsers: chrome, chrome-beta, chrome-dev, chrome-canary, msedge, msedge-beta, msedge-dev, msedge-canary. Use beta/dev/canary to catch upcoming browser changes before they reach stable.

Why the difference?

Chrome works as installed

Chromium is open source and speaks the Chrome DevTools Protocol (CDP) natively, so any stable Chromium build can be driven without patches.

Firefox needs a patched build

Stock Firefox lacks automation APIs Playwright needs (auto-wait internals, network interception, request routing), so Playwright ships its own fork. There is no channel: 'firefox'.

Safari is closed

Safari is closed source with no protocol Playwright can use. WebKit is open source, so Playwright ships a patched WebKit: close to Safari's rendering and JS, but not Safari.

Interview angle: “Can Playwright automate Safari?”

No. It automates WebKit, the engine Safari uses, which covers most CSS, JavaScript and rendering behaviour but not Safari-only features (extensions, Keychain, autofill). For real Safari, use Selenium with SafariDriver or a cloud grid with real Safari machines.

Check what is really being launched 
DEBUG=pw:browser npx playwright test

The log shows the executable path: Playwright's own cache (ms-playwright/firefox-…) for bundled browsers, or your system Chrome path when you use channel: 'chrome'.

When to use what

  • Everyday development → chromium (bundled, fast, consistent)
  • Chrome-specific bug → channel: 'chrome'; enterprise Edge → channel: 'msedge'
  • Cross-browser CI → three projects: chromium, firefox, webkit
  • Real Safari → a cloud provider with real Safari machines

Projects: same tests, many browsers

Each entry in projects is one named configuration. Playwright runs every test once per project, in parallel, and reports results per project.

projects: [
  { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
  { name: 'Google Chrome', use: { ...devices['Desktop Chrome'], channel: 'chrome' } },
  { name: 'firefox', use: { ...devices['Desktop Firefox'] } },
  { name: 'webkit',  use: { ...devices['Desktop Safari'] } },
  { name: 'mobile-safari', use: { ...devices['iPhone 15'] } },
  // Brave: Chromium-based, not officially supported, needs its path
  { name: 'brave', use: { browserName: 'chromium',
      launchOptions: { executablePath: '/Applications/Brave Browser.app/Contents/MacOS/Brave Browser' } } },
],
npx playwright test                                  # all projects
npx playwright test --project="Google Chrome"        # one project
npx playwright test --project=chromium --project=firefox

Log in once: a setup project + storageState

Logging in through the UI in every test is slow. Instead, a setup project logs in once and saves cookies and local storage to a JSON file. Every browser project depends on it and starts already signed in. This is the login pattern the Playwright docs recommend.

// tests/auth.setup.ts
import { test as setup } from '@playwright/test';
const authFile = 'playwright/.auth/user.json';

setup('authenticate', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('admin@test.com');
  await page.getByLabel('Password').fill('pass123');
  await page.getByRole('button', { name: 'Login' }).click();
  await page.waitForURL('**/dashboard');
  await page.context().storageState({ path: authFile });
});
// playwright.config.ts
projects: [
  { name: 'setup', testMatch: /.*\.setup\.ts/ },
  { name: 'chromium',
    use: { ...devices['Desktop Chrome'],
           storageState: 'playwright/.auth/user.json' },
    dependencies: ['setup'] },
  { name: 'firefox',
    use: { ...devices['Desktop Firefox'],
           storageState: 'playwright/.auth/user.json' },
    dependencies: ['setup'] },
],
Keep the auth file out of git

It holds real session cookies. Add playwright/.auth to .gitignore.

07

Workers, parallelism and retries

Each worker is a separate OS process with its own browser. By default, files run in parallel across workers, while tests inside one file run in order in the same worker. fullyParallel: true lets individual tests spread across workers too.

Option (config / CLI)What it doesDefault
workers: 4 · --workers=4Number of parallel worker processesHalf the CPU cores
fullyParallel: true · --fully-parallelRun tests inside a file in parallel toofalse
retries: 2 · --retries=2Re-run a failed test up to N more times0
maxFailures: 5 · -x (stop at first)Stop the whole run after N failuresno limit
--repeat-each=3Run every test N times: great for hunting flakes1
--last-failedRe-run only the tests that failed last time–

A test that fails and then passes on retry is reported as flaky, not passed. Treat flaky as a bug to fix, not a result to accept. The usual setup is retries: process.env.CI ? 2 : 0 so flakes don't hide on your own machine.

08

Timeouts and auto-waiting

Before every action Playwright waits automatically until the element is ready. Step through what happens inside one click() while the page is still loading.

WhatDefault in Playwright TestChange it
Whole test (incl. hooks and fixtures)30 stimeout in config, test.setTimeout(ms), test.slow()
expect(…) web-first assertions5 s, retryingexpect: { timeout }, or { timeout } on one assertion
Actions: click(), fill(), …no own limit, capped by the test timeoutuse: { actionTimeout } or { timeout }
page.goto(), waitForURL()no own limit, capped by the test timeoutuse: { navigationTimeout } or { timeout }
Whole runno limitglobalTimeout, --global-timeout
Prefer
  • await expect(locator).toBeVisible()
  • await locator.waitFor() (all locator types)
  • await page.waitForURL('**/dashboard')
  • await page.waitForResponse('**/api/cart')
Avoid
  • page.waitForTimeout(5000): a hard sleep, slow and still flaky
  • page.waitForSelector(): CSS/XPath only; locators already wait
  • waitForLoadState('networkidle') as a habit

Part 2 · Locators

How Playwright finds elements, and how to choose locators that survive the next redesign.

09

What a locator is

A strategy, not an element

page.getByRole('button') only describes how to find something. Nothing is searched yet.

Lazy

The search happens fresh each time you act or assert, so it always sees the current page.

Auto-waiting

Actions and assertions retry until the element is ready or the timeout hits.

Strict

An action fails if the locator matches more than one element, instead of silently clicking the first.

12

CSS and XPath: when they are fine

page.locator() takes CSS (the default) or XPath (starting with // or xpath=). Both are fast and powerful, but they describe how the page is built, so they break when the structure changes.

Good CSS: stable attributes 
page.locator('#email')
page.locator('[type="email"]')
page.locator('[data-testid="login-btn"]')
page.locator('button:has-text("Submit")')
page.locator('.btn.primary')   // only if classes are meaningful
Brittle CSS: structure and position 
page.locator('div > span > a')
page.locator('button:nth-child(1)')
page.locator('li:nth-of-type(3)')
page.locator('.container .row .col button')
page.locator('.css-1x2y3z4-MuiButton-root')  // generated
XPath only when nothing else works 
// relative navigation to a parent or sibling
page.locator('//input[@id="email"]/parent::form')
page.locator('//label[text()="Email"]/following-sibling::input')
page.locator('//a[contains(text(), "Forgot")]')
Never 
page.locator('/html/body/div[1]/div/main/section/button')
page.locator('//div[1]/div[2]/span[3]/button')
page.locator('//div/div/div/div/button')

The same Login button, five ways, from best to last resort:

// <button id="loginBtn" class="primary" data-testid="loginBtn">Login</button>
page.getByRole('button', { name: 'Login' })   // 1 best
page.getByText('Login')                       // 2
page.getByTestId('loginBtn')                  // 3
page.locator('#loginBtn')                     // 4
page.locator('//button[@id="loginBtn"]')      // 5 last resort

13

Chaining, filtering and lists

Narrow a locator step by step, the way you'd describe an element to a person: “the Edit button in the row for John Doe”.

// scope: search only inside the form
const form = page.locator('#login-form');
await form.getByLabel('Email').fill('test@test.com');
await form.getByRole('button', { name: 'Login' }).click();

// filter by text, or by a child locator
await page.getByRole('listitem').filter({ hasText: 'Product 2' }).getByRole('button', { name: 'Add to cart' }).click();
await page.locator('article').filter({ has: page.getByRole('heading', { name: 'News' }) }).click();

// a table row by its content, then a button in it
await page.getByRole('row', { name: /John Doe/ }).getByRole('button', { name: 'Edit' }).click();

// position: only when order really matters
await page.getByRole('button').first().click();
await page.getByRole('button').last().click();
await page.getByRole('button').nth(1).click();          // 2nd one (0-based)

Working with many elements

const buttons = page.getByRole('button');
const count = await buttons.count();
for (let i = 0; i < count; i++) {
  console.log(await buttons.nth(i).textContent());
}
const texts = await buttons.allTextContents();      // all at once
await expect(buttons).toHaveCount(2);                // assert, with retry
Common mistakes

❌ page.locator('button'): too generic, will hit strict mode → ✅ getByRole('button', { name: 'Submit' })

❌ page.locator('button').click() without await: the test moves on before the click happens → ✅ await …click()

❌ Styling classes like .btn-blue: they change with every redesign → ✅ semantic locators

14

Flaky locators: it's not the code

Most “random” test failures come from locator choices, not from Playwright or the app. The classic story: CI is green on Monday; on Friday someone adds a promo banner <div>, and a position-based locator now points at nothing.

Why it happens

Old habits

Tutorials start with findElement(By.xpath(…)), and that habit sticks.

DevTools makes it easy

Right-click → Copy XPath gives //div[@id='app']/div/div[2]/div[1]/button: precise-looking, but a time bomb.

It works… at first

The test passes today. The pain arrives two sprints later, when the UI changes.

Red flags in code review

Red flagExample
nth-child / nth-of-type'div:nth-child(3) > span:nth-of-type(2)'
Auto-generated class names'.css-1x2y3z4-MuiButton-root'
Long XPath chains'//div/div/div/div/button'
Absolute paths from /html'/html/body/div[1]/div/main/…'
Vague contains() text'//button[contains(text(), "Click")]'
Stacked partial attribute checks'[class*="btn"][class*="primary"]'

From brittle to resilient

Fragile 
// login form
await page.locator('#root > div > div:nth-child(1) > input').fill('u@test.com');
await page.locator('#root > div > button.submit-btn').click();
// navigation
await page.locator('nav > ul > li:nth-child(3) > a').click();
// data table
await page.locator('table tbody tr:nth-child(2) td:nth-child(4) button').click();
Resilient 
// login form
await page.getByLabel('Email').fill('u@test.com');
await page.getByRole('button', { name: 'Login' }).click();
// navigation
await page.getByRole('navigation').getByRole('link', { name: 'Products' }).click();
// data table
await page.getByRole('row', { name: /John Doe/ }).getByRole('button', { name: 'Edit' }).click();

“Your test scripts should read like a user manual, not a DOM tree.”

15

Picking the right locator, every time

Answer the questions top to bottom. Stop at the first yes.

The data-testid contract

When the accessible name isn't unique (a list where every item has an Edit button), ask a developer for a test hook. It takes them seconds and saves you hours of debugging.

<!-- developer adds -->
<button data-testid="checkout-submit">Submit</button>
<button data-testid="newsletter-submit">Submit</button>
// your test is now unambiguous
await page.getByTestId('checkout-submit').click();
  • Use meaningful names: user-profile-edit-btn, not btn-123.
  • Make it a team standard: put it in the pull-request checklist.
  • Use it sparingly: accessibility locators still come first.
Let Playwright suggest the locator

The Pick locator button in codegen, UI mode and the VS Code extension hovers an element and gives you the role-based locator Playwright itself would use.

Making it stick in a team

“Developers won't add test attributes.”

Show the flaky-test numbers, add it to the definition of done, and lead by example on new features. Accessible labels also help screen-reader users.

“It takes too long to refactor everything.”

Don't boil the ocean: write new tests the right way, fix old ones as they break, and audit your five flakiest tests first.

Part 3 · Assertions

Checking results with web-first assertions that wait and retry.

16

Assertions with expect

Web-first assertions take a locator or page and retry until the condition is true or the timeout (5 s by default) runs out. Always await them.

GroupAssertionPasses when
Visibility
toBeVisible()The element is visible
toBeHidden()Hidden, or not in the DOM
toBeAttached()In the DOM, visible or not
Text and value
toHaveText('Welcome')Full text matches (string or regex; an array for a list)
toContainText('Welcome')Text contains the substring
toHaveValue('a@b.com')Input has this value
State
toBeEnabled() · toBeDisabled()Enabled / disabled
toBeChecked()Checkbox or radio is checked
toBeEditable() · toBeFocused() · toBeEmpty()Editable / has focus / no text or value
Attributes
toHaveAttribute('type', 'submit')Attribute has this value
toHaveClass(/primary/) · toHaveId('submit-form')Class / id matches
toHaveCSS('color', 'rgb(255, 0, 0)')Computed style matches
toHaveCount(5)The locator matches exactly N elements
Page
expect(page).toHaveTitle(/dashboard/i)Title matches
expect(page).toHaveURL(/.*dashboard/)URL matches

Modifiers

await expect(locator).not.toBeVisible();                     // negate
await expect.soft(locator).toHaveText('Hi');                 // keep going; fail the test at the end
await expect(locator).toBeVisible({ timeout: 15000 });       // longer wait for this one check
Don't assert on a snapshot of the page

expect(await locator.isVisible()).toBe(true) checks once and never retries. await expect(locator).toBeVisible() waits for the page to catch up.

Trace viewer: replay a failure

A trace records every action with DOM snapshots before and after, network calls, console messages, the source line and screenshots. Open it after a CI failure and see exactly what the test saw. Click the actions in this mock-up.

npx playwright test --trace on                   # record every test (heavy)
npx playwright test --trace retain-on-failure    # keep traces of failures only
npx playwright show-trace test-results/…/trace.zip
npx playwright show-report                       # traces are linked from the HTML report

In the config, trace: 'on-first-retry' is the common CI choice: no cost on green runs, full detail when a test flakes. Traces can also be opened at trace.playwright.dev; the file stays in your browser.

Screenshots and videos

// one element
await page.getByRole('button', { name: 'Login' })
  .screenshot({ path: 'screenshots/login-btn.png' });

// what is visible in the viewport
await page.screenshot({ path: 'screenshots/viewport.png' });

// the whole scrollable page
await page.screenshot({ path: 'screenshots/full.png', fullPage: true });
// playwright.config.ts: automatic capture
use: {
  screenshot: 'only-on-failure',   // 'on' | 'off' | 'only-on-failure'
  video: 'retain-on-failure',      // 'on' | 'off' | 'retain-on-failure' | 'on-first-retry'
  trace: 'on-first-retry',
},

Automatic screenshots and videos land in test-results/ (one folder per test, set by outputDir) and are attached to the HTML report. Videos are .webm files you can open in any browser.

Attach your own screenshot to the report

test.afterEach(async ({ page }, testInfo) => {
  if (testInfo.status !== testInfo.expectedStatus) {
    await testInfo.attach('screenshot', {
      body: await page.screenshot({ fullPage: true }),
      contentType: 'image/png',
    });
  }
});

Use unique names (e.g. with Date.now() or the test title) when you save files yourself, so runs don't overwrite each other.

23

Sharding and CI

Workers split tests across CPU cores on one machine; shards split them across several machines. Each shard writes a blob report, and one final step merges them into a single HTML report.

npx playwright test --shard=1/3 --reporter=blob   # on machine 1
npx playwright test --shard=2/3 --reporter=blob   # on machine 2
npx playwright test --shard=3/3 --reporter=blob   # on machine 3
npx playwright merge-reports --reporter=html ./all-blob-reports

GitHub Actions, sharded

# .github/workflows/playwright.yml
name: Playwright Tests
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        shard: [1/4, 2/4, 3/4, 4/4]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npx playwright test --shard=${{ matrix.shard }} --reporter=blob
      - uses: actions/upload-artifact@v4
        if: ${{ !cancelled() }}
        with:
          name: blob-report-${{ strategy.job-index }}
          path: blob-report
