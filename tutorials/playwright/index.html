Why @playwright/test?

Playwright Test is a complete test runner, not just a browser library: fixtures, parallel runs, retries, browsers and reports come built in. No Jest, Mocha or TestNG needed.

🧩Fixtures

Every test gets a fresh, isolated page.

⚡Parallel

Test files spread across worker processes.

🌐Projects

Same tests in Chromium, Firefox and WebKit.

📊Reports & traces

HTML report, screenshots, videos, time-travel traces.

npm init playwright@latest      # config, tests/ folder and an example test
npx playwright test             # run everything: headless, in parallel
npx playwright show-report      # open the HTML report
  • One install gives you runner + browsers + tooling
  • Tests are isolated and parallel by default
  • npx playwright test runs everything

Tests, hooks and annotations

Hooks wrap your tests: beforeEach/afterEach around every test, beforeAll/afterAll once around the group.

  • Each test gets a brand-new page: no state leaks between tests
  • beforeAll runs once per worker, not once per run
  • Annotations like test.skip and test.slow change how a test runs
Go deeper: a full spec file and every annotation 
import { test, expect } from '@playwright/test';

test.describe('Login module', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('/login');
  });

  test('valid login', { tag: '@smoke' }, async ({ page }) => {
    await page.getByLabel('Email').fill('admin@test.com');
    await page.getByLabel('Password').fill('pass123');
    await page.getByRole('button', { name: 'Login' }).click();
    await expect(page).toHaveURL(/dashboard/);
  });
});
AnnotationEffect
test.skip('why') · test.skip(browserName === 'firefox', 'why')Skip now, or only when the condition is true. The reason is recorded in the report
test.only(…)Run only this test. Guard CI with --forbid-only
test.fixme('why')Known broken: skipped, marked “fixme”
test.fail('why')Expected to fail; the run fails if it passes
test.slow('why')Triples this test's timeout
test.describe.configure({ mode: 'serial' })Run the group in order; one failure skips the rest
test.describe.configure({ mode: 'parallel' })Run tests inside this file in parallel

Fixtures: what { page } really is

The things your test asks for (page, context, request…) are fixtures: set up just before the test, handed over, and cleaned up after it.

  • page and context are new for every test
  • browser is shared by the tests in one worker
  • Your own fixtures turn page objects into one-word arguments

// fixtures/base.ts
import { test as base } from '@playwright/test';
import { LoginPage } from '../pages/LoginPage';

export const test = base.extend<{ loginPage: LoginPage }>({
  loginPage: async ({ page }, use) => {
    await use(new LoginPage(page));   // code before use() = setup, after = teardown
  },
});
export { expect } from '@playwright/test';

// tests/login.spec.ts
test('login', async ({ loginPage }) => {
  await loginPage.login('admin@test.com', 'pass123');
});

playwright.config.ts: the control panel

One file decides where tests live, how long they may take, how many run at once, which browsers run them and what gets recorded. Click any line.

  • Top-level options control the run; use controls each browser context
  • Use process.env.CI to be stricter on CI
  • Different needs? Separate files, picked with --config

Which browsers can Playwright drive?

Your installed Chrome and Edge: yes. Firefox and WebKit: only Playwright's own patched builds. Safari: never. Pick one to see why.

  • channel: 'chrome' / 'msedge' use your installed browser
  • There is no channel: 'firefox'
  • WebKit ≈ Safari's engine, but it is not Safari
Go deeper: channels, the “why”, and the interview answer

Channels: chrome, chrome-beta, chrome-dev, chrome-canary, msedge, msedge-beta, msedge-dev, msedge-canary. Use beta/dev/canary to catch browser changes before they ship.

  • Chrome works as installed because Chromium speaks the Chrome DevTools Protocol (CDP) natively.
  • Firefox needs a patched build: stock Firefox lacks APIs Playwright relies on (auto-wait internals, network interception, routing).
  • Safari is closed source with no protocol Playwright can use. WebKit is open source, so Playwright patches that.

“Can Playwright automate Safari?” No: it automates WebKit, Safari's engine. That covers most CSS, JS and rendering, but not Safari-only features (extensions, Keychain, autofill). For real Safari use Selenium + SafariDriver or a cloud grid.

See which binary really launches: DEBUG=pw:browser npx playwright test.

Projects, and logging in only once

Each project runs every test with its own settings (usually one per browser). A setup project logs in once and saves the session for all of them.

  • Tests run once per project, in parallel
  • dependencies: ['setup'] runs setup first
  • storageState = saved cookies + storage; keep the file out of git
Go deeper: the config and the setup test 
// playwright.config.ts
projects: [
  { name: 'setup', testMatch: /.*\.setup\.ts/ },
  { name: 'chromium', dependencies: ['setup'],
    use: { ...devices['Desktop Chrome'], storageState: 'playwright/.auth/user.json' } },
  { name: 'firefox', dependencies: ['setup'],
    use: { ...devices['Desktop Firefox'], storageState: 'playwright/.auth/user.json' } },
],
// tests/auth.setup.ts
import { test as setup } from '@playwright/test';

setup('authenticate', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('admin@test.com');
  await page.getByLabel('Password').fill('pass123');
  await page.getByRole('button', { name: 'Login' }).click();
  await page.waitForURL('**/dashboard');
  await page.context().storageState({ path: 'playwright/.auth/user.json' });
});
npx playwright test --project=chromium --project=firefox   # pick projects

Opera and Brave are Chromium-based; they usually work with browserName: 'chromium' plus launchOptions.executablePath, but aren't officially supported.

Workers, parallelism and retries

Each worker is a separate process with its own browser. Files run in parallel; tests inside a file run in order, unless you turn on fullyParallel.

  • Default workers = half your CPU cores
  • Failed, then passed on retry = flaky, not passed
  • Usual setup: retries: process.env.CI ? 2 : 0

Auto-waiting, so you never sleep()

Before every action Playwright waits until the element is attached, visible, stable, enabled and able to receive the click. Step through one click().

  • Test timeout: 30 s · expect timeout: 5 s
  • Actions and navigation are capped by the test timeout
  • Never waitForTimeout(5000): wait for a condition instead
Go deeper: every timeout and the waits to prefer
WhatDefaultChange it
Whole test (incl. hooks)30 stimeout, test.setTimeout(), test.slow()
expect(…)5 s, retryingexpect: { timeout }, or per assertion
Actions (click, fill…)capped by test timeoutuse: { actionTimeout }
goto, waitForURLcapped by test timeoutuse: { navigationTimeout }
Whole runno limitglobalTimeout

✅ await expect(locator).toBeVisible(), locator.waitFor(), page.waitForURL(), page.waitForResponse()
❌ page.waitForTimeout() (hard sleep), page.waitForSelector() (locators already wait)

What a locator is

A locator is a recipe for finding an element, not the element itself. It searches fresh every time you use it, waits until it can act, and refuses to guess when several elements match.

  • Lazy: nothing is searched until you act or assert
  • Auto-waiting: retries until ready or timeout
  • Strict: more than one match is an error

Locator priority: test like a user

Find elements the way a user does, by role and name, label or visible text. Users never see CSS classes or how deep a <div> is nested.

  • 1st choice: getByRole(role, { name })
  • Then label, text or placeholder; then getByTestId
  • CSS and XPath last

CSS, XPath, and narrowing down

CSS and XPath describe how the page is built, so they break when it changes. Prefer narrowing a user-facing locator step by step: “the Edit button in John's row”.

  • OK: #id, real attributes like [type="email"]
  • Avoid: nth-child, generated classes, /html/body/…
  • Narrow with .filter(), scoping, then .first()/.nth() last
Go deeper: good vs brittle selectors, lists, common mistakes
Fine 
page.locator('#email')
page.locator('[data-testid="login-btn"]')
page.locator('//input[@id="email"]/parent::form')
Brittle 
page.locator('div > span > a')
page.locator('button:nth-child(1)')
page.locator('/html/body/div[1]/div/main/button')
const buttons = page.getByRole('button');
await expect(buttons).toHaveCount(2);              // assert, with retry
const texts = await buttons.allTextContents();     // all at once
await page.locator('.item').visible().first().click();   // only visible ones (1.63+)

❌ Forgetting await: page.locator('button').click() moves on before the click happens.

Flaky locators: it's not the code

Most “random” failures are locator choices. Classic case: someone adds a promo banner, and every position-based locator now points somewhere else. Ship the release below.

  • Position (nth-child, [3]) breaks when anything is added
  • “Copy XPath” from DevTools gives you a time bomb
  • Tests should read like a user manual, not a DOM tree
Go deeper: red flags to reject in code review
Red flagExampleInstead
Position'li:nth-child(3) > a'getByRole('link', { name: 'Products' })
Generated classes'.css-1x2y3z4-MuiButton-root'Role + name
Long XPath chains'//div/div/div/button'Role, label, text
Absolute paths'/html/body/div[1]/…'Anything else
Vague text'//button[contains(text(),"Click")]'Exact accessible name

Pick the right locator, every time

Ask four questions, top to bottom, and stop at the first yes.

  • Not unique by name? Ask for a data-testid
  • Name test ids by meaning: checkout-submit, not btn-123
  • Let Playwright suggest: Pick locator in codegen, UI mode, VS Code
Go deeper: the data-testid contract 
<!-- developer adds -->
<button data-testid="checkout-submit">Submit</button>
<button data-testid="newsletter-submit">Submit</button>

// your test is now unambiguous
await page.getByTestId('checkout-submit').click();

Make it a team rule (in the pull-request checklist), but use it sparingly: accessible locators still come first, and accessible labels help screen-reader users too.

Assertions that wait

Web-first assertions take a locator and retry until true, up to 5 s. Always await them, and never check a one-off snapshot like isVisible().

  • await expect(locator).toBeVisible() retries; expect(await locator.isVisible()) doesn't
  • .not negates, expect.soft keeps going
  • { timeout: 15000 } for one slow check

Record tests, then step through them

Codegen writes a test while you click. UI mode is your daily workbench. --debug pauses so you can step action by action. Pick a tool.

  • npx playwright codegen <url> records
  • npx playwright test --ui for writing and fixing
  • await page.pause() stops at an exact line

Trace viewer: replay a failure

A trace records every action with DOM snapshots, network, console and source. Open a CI failure and see exactly what the test saw. Click the actions.

  • trace: 'on-first-retry' is the usual CI setting
  • npx playwright show-trace trace.zip opens one
  • Or drop it on trace.playwright.dev: the file stays in your browser

Screenshots, videos and reports

Let the config capture evidence only when something fails, and let reporters turn results into something humans and CI tools can read.

// playwright.config.ts
use: {
  screenshot: 'only-on-failure',
  video: 'retain-on-failure',
  trace: 'on-first-retry',
},
reporter: [['list'], ['html', { open: 'never' }]],
// by hand
await page.screenshot({ path: 'page.png' });
await page.screenshot({ path: 'all.png', fullPage: true });
await page.getByRole('button', { name: 'Login' })
  .screenshot({ path: 'login-btn.png' });
  • Files land in test-results/ and are attached to the HTML report
  • Video and trace accept the same modes (since 1.61)
  • Local default reporter: list; on CI: dot

Run the right tests, fast, in CI

Tags pick which tests run. Shards split them across machines. Each shard writes a blob report, and one step merges them.

  • { tag: '@smoke' } + --grep @smoke
  • --shard=1/3 on each machine, --reporter=blob
  • npx playwright merge-reports builds one report
Go deeper: filtering commands and a GitHub Actions file 
npx playwright test tests/login.spec.ts:15       # one test by line
npx playwright test -g "valid login"             # by title
npx playwright test --grep @smoke                # by tag
npx playwright test --grep-invert @slow          # everything but (-G for short)
npx playwright test --list                       # just list
# .github/workflows/playwright.yml
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix: { shard: [1/4, 2/4, 3/4, 4/4] }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npx playwright test --shard=${{ matrix.shard }} --reporter=blob
      - uses: actions/upload-artifact@v4
        if: ${{ !cancelled() }}
        with: { name: blob-${{ strategy.job-index }}, path: blob-report }

Since 1.65 a sharded run fails with “No tests found” if no shard has tests; add --pass-with-no-tests if that is expected.
